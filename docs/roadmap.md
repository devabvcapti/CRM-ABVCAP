### Incidente — 500 em produção (2026-10-02)

- **Sintoma**: `https://crm-abvcap.vercel.app` retornava "Internal Server Error" em toda rota, logo após os commits de integração do Supabase.
- **Causa raiz**: `NEXT_PUBLIC_SUPABASE_URL`/`NEXT_PUBLIC_SUPABASE_ANON_KEY` foram adicionadas só em `.env.local` (gitignored, local), nunca nas Environment Variables do projeto Vercel. `src/proxy.ts` chama `updateSession` (Supabase) em **toda rota** (matcher só exclui `/api`, `/trpc`, `/_next`, `/_vercel` e arquivos com ponto) — com as env vars `undefined`, `createServerClient` do `@supabase/ssr` lança `"Your project's URL and Key are required to create a Supabase client!"`, derrubando o site inteiro no middleware, antes de qualquer página renderizar.
- **Diagnóstico**: `vercel env ls production` confirmou **zero env vars configuradas em qualquer ambiente** (não só essas duas); `vercel logs` confirmou o stack trace exato citado acima.
- **Correção**: `NEXT_PUBLIC_SUPABASE_URL` e `NEXT_PUBLIC_SUPABASE_ANON_KEY` adicionadas via `vercel env add` nos três ambientes (production/preview/development) — a anon key precisou do flag explícito `--type config` porque a CLI a reconheceu como "parece uma credencial" e pede escolha explícita entre `secret` (privada) ou `config` (pública); **`config` é o certo aqui**, é assim que o client do navegador funciona — a proteção real é RLS no banco, não o sigilo da anon key. Redeploy de produção (`vercel --prod`) disparado em seguida, já que variáveis `NEXT_PUBLIC_*` são embutidas em build-time — só adicionar a env var não afeta um build já existente.
- **Verificado**: `vercel curl` na produção depois do redeploy retorna o HTML completo da home (antes retornava o 500).
- **Lição para toda env var nova daqui pra frente**: `.env.local`/`.env.example` cobre o ambiente local — **sempre replicar em `vercel env add` para production (e preview/development) no mesmo passo**, nunca como etapa separada/depois. Registrado também em `ai-context/skills/01-scaffolding.md`.
