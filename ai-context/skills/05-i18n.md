# Skill: internacionalizacao

## Objetivo
Externalizar 100% das strings de interface com `next-intl`, gerenciando catálogos pt-BR/en-US paritários desde a primeira tela. O retrofit posterior exigiria refatoração profunda e custosa de dezenas de telas.

## Pré-condições
- Skill 01 concluída (`next-intl` instalado, rotas `[locale]` configuradas).
- Nenhuma tela desenvolvida antes desta skill estar ativa.
- **Skills do Claude Code a invocar**: `vercel:nextjs` (roteamento `[locale]` do App Router); não há skill dedicada de `next-intl` neste ambiente.
- **Documentação via Context7**: `ctx7 library "next-intl" "..."` para configuração de roteamento por locale e catálogos de mensagens — usar isso em vez de memória de treinamento para esta lib específica.

## Implementado em 2026-10-01 — ver antes de mexer em i18n de novo
- Este projeto está no **Next.js 16**, que renomeou `middleware.ts` para **`src/proxy.ts`** (export `proxy`/`config`, mesma lógica de antes). O próprio next-intl (≥4.4) já documenta isso: "`proxy.ts` was called `middleware.ts` up until Next.js 16". Usar um exemplo que ainda fale em `middleware.ts` é desatualizado para este projeto — reconfirmar via `ctx7` se parecer divergente.
- A doc oficial do next-intl marca `requestLocale`/`setRequestLocale` como **legado, não mais recomendado**, em favor de **`next/root-params`** (`import { locale } from "next/root-params"`, usado em `src/i18n/request.ts` e em `src/app/[locale]/layout.tsx` para `<html lang={await locale()}>`). Foi isso que implementamos — não regredir para o padrão legado sem motivo.
- `[locale]` é o **segmento raiz** da árvore de rotas (`src/app/[locale]/layout.tsx` é o root layout de verdade — não existe `src/app/layout.tsx` separado). `generateStaticParams` no layout gera `pt-BR` e `en-US` estaticamente.
- Arquivos-base já existem: `src/i18n/routing.ts` (locales + defaultLocale), `src/i18n/navigation.ts` (`Link`/`redirect`/`usePathname`/`useRouter` com locale-awareness), `src/i18n/request.ts`, `src/proxy.ts`, `next.config.ts` (envolvido com `createNextIntlPlugin`).

## Passos
1. Criar/atualizar chaves em `src/messages/pt-BR.json` e `src/messages/en-US.json` **simultaneamente**, nunca uma sem a outra.
2. Consumir toda string de UI via hook/função de tradução do `next-intl` (`useTranslations`/`getTranslations`) — proibido texto literal em JSX. Usar `@/i18n/navigation` (não `next/link`/`next/navigation`) para qualquer link/navegação interna, para preservar o prefixo de locale.
3. Para dados dinâmicos vindos do banco (ex.: status, tipo), mapear o código persistido para a chave de tradução na camada de apresentação, nunca persistir o texto traduzido no banco.
4. Configurar o CI para falhar o build se as chaves de `pt-BR.json` e `en-US.json` não forem estritamente paritárias.

## Padrões obrigatórios
- Nomenclatura técnica em inglês; conteúdo de negócio sempre via catálogo.
- Nenhuma mensagem de erro ao usuário hardcoded, incluindo validações de formulário (Zod) — usar mapas de mensagens traduzíveis.
- Datas, números e moeda formatados de acordo com o locale ativo.

## Checklist de aceite

- [ ] `pt-BR.json` e `en-US.json` com o mesmo conjunto de chaves (verificado no CI).

- [ ] Mensagens de erro de validação (Zod) traduzidas nos dois idiomas.
